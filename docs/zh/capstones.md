# 综合项目

四个项目都来自企业 JD 里反复出现的交付场景。选一个做主作品，把前面实验的成果接进去，再挑一个方向做出有实测数据的深度。数据用公开许可的资料、自己造的可公开数据，或者明确授权的数据。

## P1 企业知识服务

**要做什么：** 不同角色的员工查询制度、产品手册或技术文档，回答附带出处；资料可以更新，也可以撤回。没有真实企业数据时，可以用公开技术文档，自己设定部门和权限来模拟。

- **流程：** 同步资料 → 解析并记录版本 → 按权限建索引 → 检索和重排 → 生成带引用的回答 → 收集纠错反馈。
- **用到的模块：** 06 检索与 RAG、02 数据库与多租户、05 模型调用、11 评测与追踪、14 部署。起步只需要 FastAPI、PostgreSQL/pgvector、BM25、一个模型适配层和一个观测工具。
- **要做的对比：** 关键词检索、向量检索、混合检索加重排。按资料来源和问题类型划分 dev/test，分别评测检索、回答是否有依据、无答案、资料过期和越权这几类情况。
- **往深做：** 增量更新做到幂等、删除后旧内容不再出现、索引版本切换、检索前就按权限过滤、出故障时降级或回滚。
- **要交的证据：** 文档和标注的版本、每道题的结果、权限测试、p50/p95 延迟、每次成功回答的成本、界面和运维手册。

## P2 带业务操作的流程 Agent

**要做什么：** 处理客服工单或供应商请求：查政策、读订单状态、提出处理方案，需要时请人确认，再执行有审计记录的操作。外部系统先用独立的模拟服务，之后换成授权的测试环境。

- **流程：** 收到请求 → 记录任务状态并调用工具 → 提出方案、等待确认 → 提交到外部系统 → 对账并通知 → 收集反馈。
- **用到的模块：** 07 Agent harness、08 LangGraph 与耐久工作流、10 MCP 与权限、02 幂等与队列、11–14 评测与上线。
- **要做的对比：** 规则流程、单 Agent、带规划或多 Agent 协作的版本。模型、工具和预算保持一致，比较成功率、人工接管率、工具调用错误和成本。
- **往深做：** 持久化状态、审批绑定具体动作（参数变了要重新审批）、幂等键、并发与租约、外部调用结果未知时怎么处理、撤销、重放与对账。
- **要交的证据：** 状态流转图、MCP 工具、跨进程的故障演练、重复投递测试、审计记录，以及用户能看到的恢复流程。

## P3 文档处理与人工复核

**要做什么：** 对公开或合成的单据、申请材料做分类、字段抽取和核验；置信度低的结果交给人工复核，修正结果回流进数据集。

- **流程：** 接收文件 → 解析、OCR 或视觉模型 → 按 schema 抽取 → 业务规则校验 → 人工复核队列 → 导出或回写。
- **用到的模块：** 05.6 多模态、02 异步任务与数据、11 标注与评测、14 交互与治理；12 的微调或蒸馏可选。
- **要做的对比：** 规则或传统解析、通用大模型、针对任务适配过的模型。分别统计字段、整份文档和业务规则三层的正确率，比较送人工复核的比例与错误率、成本的关系。
- **往深做：** 格式和大小限制、取消任务、批处理幂等、每个字段能追溯到原文位置、复核意见冲突、脱敏和数据保留策略。
- **要交的证据：** 标注规范、按类型整理的失败案例、复核界面、导出格式约定、版本记录、吞吐和延迟，以及人工工作量估算。

## P4 小模型服务与行为优化

**要做什么：** 为分类、结构化抽取或范围有限的工具选择部署一个小模型，在保证任务质量的前提下降低成本或延迟。

- **流程：** 准备数据和基线 → 本地跑模型 → 封装成 API → SFT/LoRA 或蒸馏 → 压测 → 发布新版本。
- **用到的模块：** 03–04 模型基础、12 后训练、13 推理、11 实验、14 交付。按硬件选 llama.cpp/MLX LM 或 vLLM/SGLang。
- **要做的对比：** 只用提示词的基线、微调前后、不同精度/上下文长度/并发数。训练带来的提升和服务配置带来的变化要分开算。
- **往深做：** 数据泄漏检查、chat template 和 label mask、checkpoint 与版本、显存和 KV cache、预热、排队和回滚。
- **要交的证据：** 配置和日志、独立测试集结果、硬件和模型版本、TTFT/TPOT/吞吐/显存，以及质量和每次成功任务的成本。

## 可选扩展

想做多 Agent，就从 P2 里能拆分的任务开始，并保留单 Agent 版本做对照。Agentic RL 需要能重置的环境、可审计的奖励和没见过的测试场景。GraphRAG、长期记忆、A2A、分布式推理，等遇到具体瓶颈再加，并测出加了之后多得到什么、多花多少。

## 每个项目都要交的材料

1. [任务卡](../../templates/task-card.md)：用户、流程、输入输出、错误成本、质量要求和预算。
2. 架构和接口约定：数据流、控制流、权限流，以及状态、重试和副作用由谁负责。
3. 数据卡：来源和许可、标注规范、dev/test 怎么分组、隐私和版本。
4. [实验记录](../../templates/experiment.md)：强基线、每道题的结果、公平对比、消融、失败分类和不确定性。
5. 运维材料：干净环境安装、容器、部署、trace、压测和恢复演练、回滚和运维手册。
6. 评审记录：别人复现一遍、一次没预告的故障、一个需求变更，以及你对下一步的判断。

报告里写实测数字，并标明哪些用了真实模型、哪些是模拟环境或合成数据。质量门槛按业务的错误成本来定；越权和未授权操作单独统计，不和普通错误混在一起。评审标准见[能力评审](assessment.md)。

## 从作品到 offer：分级、上线与证据

招聘方看三件事：能不能把小产品做完并上线，能不能用测试集和基线证明效果，能不能讲清每个选择的理由。按下面三档推进，求职时至少一个作品做到 L2。

| 档位 | 参考时长 | 必须做到 |
|---|---|---|
| L1 可演示 | 1–2 周 | 核心链路可运行；10–20 条评测样例和一个基线；README 写清假设、局限和下一步 |
| L2 生产级 | 4–6 周 | 部署到公有云；IaC 与 CI/CD（staging → prod）；监控与告警；Web 界面；安全测试进 CI；有真实用户或一次试点 |
| L3 纵深 | 另加 2–4 周 | 选一个方向做出有实测结果的优化：检索质量、Agent 可靠性、成本与延迟、后训练或推理 |

**L2 的具体要求**

- **上线：** 部署到 AWS 或 Azure（加拿大银行和保险常用），用 Terraform 管理资源，GitHub Actions 走 staging → prod 并能回滚；提供公开 demo 或录屏。
- **观测：** trace、质量与成本面板，至少一条告警和一份 runbook。
- **界面：** React/Next.js，支持流式输出、引用定位和审批卡片。
- **安全：** 提示注入、越权和数据外泄测试集，通过率作为 CI 门槛。
- **真实使用：** 5–10 位真实用户或一次试点，记录使用次数、成功率、人工修正率和反馈。
- **企业系统（P2）：** 从模拟服务升级到真实 SaaS 的免费开发者环境，例如 Salesforce Developer Edition、ServiceNow 个人开发实例或 Jira Cloud 免费版。
- **AI 编程工具：** 可以使用 Claude Code、Cursor 等，在 README 写明 AGENTS.md、人工审查点，以及哪些设计决定由你负责。

**简历写法与必答追问**

| 作品 | 简历条目示例（替换为你的实测数字） | 面试官常问 |
|---|---|---|
| P1 | 为 N 份内部文档构建权限感知的问答服务；混合检索加重排使 Recall@5 从 a 提到 b，引用正确率 c%，p95 d 秒，每次成功回答成本 e 美元 | 为什么用混合检索而不是纯向量？怎样保证不越权？文档删除后多久生效？ |
| P2 | 构建带人工审批的工单 Agent；幂等键与对账让重复执行为 0，任务成功率 a%，人工接管率 b% | 审批后参数被改怎么办？外部调用超时怎么处理？为什么用或不用多 Agent？ |
| P3 | 搭建文档抽取流水线，字段准确率 a%，低置信的 b% 进入人工复核，复核工作量下降 c% | 置信度怎样校准？复核意见冲突怎么处理？怎样防止 PII 泄露？ |
| P4 | 用量化和 LoRA 优化小模型服务，在质量下降不超过 x 的前提下成本降低 y%、p95 降低 z | 质量下降怎么发现？显存怎么估算？为什么不用托管 API？ |

**按目标市场调整**

- **加拿大银行与保险：** Azure 或 AWS；补审计日志、模型风险文档和人工监督流程。
- **中国：** 先用 Dify 搭原型，再把核心流程迁到 LangGraph；接入国产模型并用 vLLM 部署。
- **北美创业公司：** TypeScript 全栈加 Agent，突出迭代速度和评测。

**起步代码：** [P1 知识服务](../../starters/p1-knowledge-service/) 和 [P2 审批 Agent](../../starters/p2-approval-agent/) 提供可运行的最小骨架（FastAPI、离线评测、测试与 Docker），在此基础上做到 L2。

## 阶段复核

开题时写清任务、数据和验收标准；做出基线后，检查评测是否可信；中期 demo 请别人运行，并挑一条失败案例分析；最终提交全部材料，现场改一个需求，并留下复现记录。模型选型、数据、评测任务和资源预算分别用[选型卡](../../templates/model-selection.md)、[数据卡](../../templates/dataset-card.md)、[任务包](../../templates/benchmark-task.md)和[预算表](../../templates/resource-budget.md)。

评测怎么接进作品，见[评测实操指南](evaluation-playbook.md)和实验 L16、L17。
