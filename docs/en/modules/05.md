## 05.1 Model APIs and provider adapters

`core` · Implement a small system and verify behavior

Prerequisites: [02.1 HTTP APIs and streaming](../modules/02.md#unit-02-1), [01.5 Testing, debugging and profiling](../modules/01.md#unit-01-5)

### Knowledge outline

- Messages, capabilities, parameters and pinned revisions
- Sync/async, streaming, usage and typed events
- Timeout, cancellation, 429s, backoff and total budgets
- Adapters, injection, fallback and test doubles
- Cache keys, versions and sensitive-data handling

### Reading and scope

[LiteLLM Documentation](https://docs.litellm.ai/docs/) — Maintainer docs for a multi-provider client layer; study exception mapping, retries/fallbacks, timeouts, streaming and usage tracking as adapter design without adopting every feature.

Unified input/output, streaming, exception mapping, retries/fallbacks, timeouts and usage tracking; then compare one provider’s native API reference.

### Build task

Build a typed provider adapter and inject failures.

### Self-check

1. What should a provider adapter layer unify (message format, streaming events, usage, error types), and which differences shouldn’t be hidden?
2. The model API returns 429. How do you design retries (exponential backoff, jitter, Retry-After, total time budget), and which errors should never be retried?
3. How do you test code that calls a model? When do recorded replays, fake clients and pinned model revisions each fit?

## 05.3 Structured output and tool execution

`core` · Implement a small system and verify behavior

Prerequisites: [05.1 Model APIs and provider adapters](../modules/05.md#unit-05-1), [01.2 Types, schemas and configuration](../modules/01.md#unit-01-2)

### Knowledge outline

- Parallel calls, partial failures, timeout and effects

### Reading and scope

[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) — Separate valid JSON, schema conformance and factual correctness.

Schema constraints, validation and errors.

### Build task

Implement two reads and one approved write, inspecting the full lifecycle.

### Self-check

1. What steps sit between a model proposing a tool call and the tool actually running (validation, authorization, execution, observation), and what does each step catch?
2. The model calls three tools in parallel; one times out and one errors. How does your executor handle this and report results back to the model?
3. Compare native structured output (strict JSON Schema) with prompting, parsing and retrying. How do you stay compatible when the schema changes?

### Build task

### Self-check

1. Explain exact versus semantic caching, and the risk that a semantic cache returns a wrong answer.
2. Routing to a small model cut costs by 40%, but complaints rose. How do you evaluate the routing policy and set fallback conditions?
3. Define cost per successful task, explain why it beats cost per call for decisions, and show how to compute it.

## 05.8 Test-time compute and verification

`core` · Diagnose failures, compare and repair

Prerequisites: [05.3 Structured output and tool execution](../modules/05.md#unit-05-3), [11.4 Experiments, A/B tests and uncertainty](../modules/11.md#unit-11-4)

### Knowledge outline

- Allocate compute across one call, decomposition, retries, self-consistency, best-of-N and search
- Separate proposal and verification; verifier errors, selection bias and amplified failures
- Reasoning depth, candidates, parallelism, tool calls and total token/time budgets
- Matched-budget quality/latency/cost frontiers and stopping or escalation
- Fixed configurations and independent trials; cached replies are not independent samples
- Validate improvements through observable outputs, actions and environment outcomes
- Reasoning-model controls: thinking budgets/effort, interleaved thinking with tools, and what reasoning content to keep or show

### Reading and scope

[Stanford CS329Z: Engineering AI Agents](https://cs329z.stanford.edu/) — Agent-engineering spine connecting frameworks, data, optimization, evaluation and safety through released material.

Published builder/optimization materials; combine11.2/11.4 for budget and reliability comparisons.

### Build task

Compare one-shot generation with one proposal/verification strategy; record total cost, latency, success and verifier mistakes.

### Self-check

1. Explain how self-consistency, best-of-N and search trade inference compute for quality, and what kind of verifier each relies on.
2. Using an LLM as the verifier for best-of-N lowered accuracy. What could cause this, and how do you test the verifier itself?
3. At a fixed token budget, compare one reasoning-model call with a small model plus best-of-5. How do you design a fair experiment and plot the quality/cost frontier?

## 05.9 Model selection and upgrade decisions

`core` · Design under constraints and defend tradeoffs

Prerequisites: [05.1 Model APIs and provider adapters](../modules/05.md#unit-05-1), [11.1 Tasks, labels and benchmark design](../modules/11.md#unit-11-1), [11.4 Experiments, A/B tests and uncertainty](../modules/11.md#unit-11-4)

### Knowledge outline

- Task capability matrix: knowledge, reasoning, tools, schemas, modalities, language and context
- Base/instruct/reasoning models and hosted/open-weight deployment choices
- Transfer from leaderboards to task distributions; model, prompt, harness and budget interact
- Quality constraints, cost, latency, data terms, deployment requirements and availability
- Capability probes, prompt/chat-template adaptation, revisions, migration and regression
- Candidate elimination, canary checks, fallback and reversible upgrade records

### Reading and scope

[CS336 Lecture 12: Evaluation](https://github.com/stanford-cs336/lectures/blob/main/lecture_12.py) — Distinguish model/system measurements, contamination, ecological validity and selection.

Lecture 12 on evaluation purpose and ecological validity; select models using a task-specific test set.

### Build task

Evaluate two candidates under the same tasks, tools and budget; deliver a selection card and upgrade/rollback exercise.

### Self-check

1. Why can’t leaderboard scores decide model selection on their own? What else matters (data terms, deployment, latency, license)?
2. After upgrading to a new model version, one task type got noticeably worse. How do you tell whether the model, the prompt or the chat template is at fault, and roll back safely?
3. Design a model selection process: capability probes, elimination criteria, canary validation and reversible upgrade records.

## 05.10 Model platforms, gateways and cloud AI services

`core` · Design under constraints and defend tradeoffs

Prerequisites: [05.1 Model APIs and provider adapters](../modules/05.md#unit-05-1)

### Knowledge outline

- Provider-side prompt caching: stable prefixes, hit rates, TTL and billing
- Batch APIs and asynchronous jobs: discounts, completion windows, retries and result reconciliation
- Rate-limit tiers, quotas, concurrency and multi-key/multi-region capacity
- Reasoning/thinking parameters, reasoning-token billing and output-length control
- OpenAI-compatible APIs and model gateways (LiteLLM, OpenRouter): unified auth, routing, auditing and fallback
- Cloud platforms (Bedrock, Vertex AI, Azure AI Foundry, Alibaba Cloud Model Studio, Volcano Engine Ark): data residency, VPC, compliance and model catalogs
- Chinese models (Qwen, DeepSeek, GLM, Kimi and others) versus overseas models: capability, price, license and availability

### Reading and scope

[OpenAI: Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching) — Official guide to provider-side prefix caching: eligibility, prefix layout, hit observability and billing; compare other vendors’ mechanisms in their docs.

Prompt caching guide and the Batch API; compare model catalogs, quotas and data terms in the Bedrock or Model Studio docs.

### Build task

Design calls for one workload: enable prompt caching and measure hit rates, move overnight jobs to a Batch API, record cost/latency changes and document primary/backup provider switching rules.

### Self-check

1. Explain when provider-side prompt caching applies (stable prefixes, TTL) and how it is billed. How would you restructure a prompt to raise the hit rate?
2. You need to summarize 100,000 documents every night. Compare the real-time API with the Batch API on cost, completion time and retrying failures.
3. Design a company model gateway: unified auth, routing, quotas, auditing and multi-provider fallback. What else applies when a China-based business calls overseas models?
