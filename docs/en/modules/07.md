## 07.1 Choosing workflows and agents

`core` · Design under constraints and defend tradeoffs

Prerequisites: [05.3 Structured output and tool execution](../modules/05.md#unit-05-3)

### Knowledge outline

- Fixed flows, dynamic decisions and hybrids
- Routing, parallelism, orchestration and evaluator loops
- Autonomy, control, complexity and verifiability
- Model/context/tool/runtime boundaries
- Single calls, long tasks, waiting and cost
- Map chaining, routing, parallelization, orchestrator-workers and evaluator-optimizer patterns to tasks

### Reading and scope

[Anthropic: Building Effective Agents](https://www.anthropic.com/research/building-effective-agents) — Substantial free design article on workflows, routing, parallelism and evaluator loops.

Full article and composable workflow patterns.

### Practical evidence

Design rule, workflow and agent alternatives for one task.

### Self-check

1. Explain the difference between a workflow and an agent, and which tasks suit each of the five patterns: prompt chaining, routing, parallelization, orchestrator-workers and evaluator-optimizer.
2. A team built a fully autonomous agent for a task a fixed flow could handle, and it is unstable and hard to test. How would you restructure it?
3. For a “handle return requests” requirement, argue which steps should be a fixed flow and which left to the model, and how you control cost and waiting time.

## 07.5 Working memory and context runtime

`core` · Diagnose failures, compare and repair

- Subagent isolation and information loss

### Reading and scope

[Anthropic: Effective Context Engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) — Engineering treatment of context selection, compaction, isolation and tool design.

Context management, compaction, isolation and external storage.

### Practical evidence

Compare inline output and artifact references on quality/cost.

### Self-check

1. What does an agent’s working memory usually contain (messages, plans, scratchpads, observations), and how should each part be compressed when context overflows?
2. On a long task, the agent keeps rereading the same large file and the context balloons. How do you fix it with artifact offloading and on-demand readback?
3. A lead agent hands a task to a subagent and key information gets lost. Analyze the information lost to isolation and design a handoff format.

## 07.8 Tiered memory, consolidation and skill learning

`advanced` · Diagnose failures, compare and repair

Prerequisites: [07.6 Long-term memory and fact lifecycle](../modules/07.md#unit-07-6), [11.1 Tasks, labels and benchmark design](../modules/11.md#unit-11-1)

### Knowledge outline

- Write/read/update ownership for working, episodic, semantic and procedural memory
- Hot/cold tiers, capacity, retrieval and paging versus context-window management
- Trajectories to reflections, reusable experience or skills; confidence and provenance
- Consolidation triggers, merging, conflicts, forgetting and rollback
- Longitudinal tasks, cross-session transfer, polluted memory and over-personalization
- Token-matched history/vector/tiered baselines with separate write, retrieval and task measurements
- Parametric versus contextual memory: adaptation and retrieval/writes have different update, withdrawal and cost boundaries

### Reading and scope

[Stanford CS329Z: Engineering AI Agents](https://cs329z.stanford.edu/) — Agent-engineering spine connecting frameworks, data, optimization, evaluation and safety through released material.

Published 14 October memory materials, alongside07.5/07.6 state and fact lifecycle.

### Practical evidence

Extract one retractable lesson from traces; test help and harm on new scenarios, including cross-session gains and costs.

### Self-check

1. Explain how tiered memory (hot and cold tiers, paging) relates to context-window management, and the basic idea behind MemGPT-style designs.
2. Lessons an agent distilled from past trajectories became polluted, and later tasks keep failing because of them. How do you detect this and roll back?
3. Design an experiment comparing full history, vector-retrieved memory and tiered memory at equal token budgets, measuring writes, retrieval and task outcomes separately.

## 07.9 Coding agents and the agent–computer interface

`advanced` · Implement a small system and verify behavior

Prerequisites: [07.3 Harnesses and agent/environment interfaces](../modules/07.md#unit-07-3), [10.5 Code, browser tools and sandboxes](../modules/10.md#unit-10-5), [11.8 Environment benchmarks and verifier validation](../modules/11.md#unit-11-8)

### Knowledge outline

- Task to workspace, localization, edits, tests and submitted artifacts
- Usability and observability of shell, file, search and browser interfaces
- Stateful tools, truncation, working directories, long commands, errors and recovery
- Repository revisions, dependencies, test environments and clean offline resets
- Patch correctness, test adequacy and environment tampering or bypass
- Interface ablations and tool feedback versus model capability

### Reading and scope

[CS329Z: Evaluation Task Assignment](https://github.com/cs329z/assignment2-evals) — Public evaluation-task exercise supporting benchmark design.

Published HW2 examples and the listed SWE-agent reading; the 30 November lecture is still upcoming at the review date.

### Practical evidence

Complete a small offline repository repair; preserve patch, tests, trajectory and clean replay, comparing two observation formats.

### Self-check

1. What is the agent–computer interface (ACI)? Why does work such as SWE-agent show that tool-interface design matters as much as model capability?
2. A coding agent makes tests pass by editing the tests. How do you prevent this in the environment and evaluation design?
3. Design a coding agent’s workspace: repository revision, dependencies, long-running commands, output truncation and a clean reset for each task.
