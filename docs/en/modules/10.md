## 10.1 Tool and connector design

`core` · Design under constraints and defend tradeoffs

Prerequisites: [02.1 HTTP APIs and streaming](../modules/02.md#unit-02-1), [05.3 Structured output and tool execution](../modules/05.md#unit-05-3)

### Knowledge outline

- Business capabilities→narrow APIs; reads/writes/effects
- Names, descriptions, arguments, errors and limits
- Registration, discovery, versions and compatibility
- Identity, approval, audit and idempotency
- Tool success, business success and call correctness

### Reading and scope

[Anthropic: Writing Effective Tools for Agents](https://www.anthropic.com/research/writing-tools-for-agents) — Engineering article on choosing tools, namespacing, returning meaningful context, token-efficient responses and error messages, and evaluating tool descriptions.

Full article: tool selection, namespacing, returned context, token efficiency, error messages and evaluation-driven iteration; check schema details against OpenAI Function Calling.

### Practical evidence

Wrap enterprise operations as three testable tools.

### Self-check

1. What makes a good tool description and parameter design? Why are several narrow, explicit tools better than one catch-all API?
2. The model often gets tool arguments wrong (date formats, enum values). How would you improve the tool definitions and error messages, rather than only the prompt?
3. Design tools for “modify a customer order”: read/write separation, idempotency, approval and auditing, and how to tell call success from business success.

## 10.6 Tool catalogs and capability retrieval

`advanced` · Implement a small system and verify behavior

Prerequisites: [10.1 Tool and connector design](../modules/10.md#unit-10-1), [06.3 Lexical, vector and ANN indexes](../modules/06.md#unit-06-3)

### Knowledge outline

- Context costs of full catalogs versus task retrieval and hierarchical routing
- Descriptions, schemas, versions, aliases and retrieval indexes
- Filter authorized capabilities before retrieval and action selection
- Separate relevant-tool recall, argument validity, execution and task outcomes
- Catalog changes, caches, invalidation, wrong tools and naming ambiguity
- Provenance, malicious descriptions and dynamic-discovery trust boundaries

### Reading and scope

[Stanford CS329Z: Engineering AI Agents](https://cs329z.stanford.edu/) — Agent-engineering spine connecting frameworks, data, optimization, evaluation and safety through released material.

Published 5 October tool-use material on API scale, discovery and evaluation, applied to 10.1 contracts.

### Practical evidence

Compare full-catalog and retrieval designs; measure recall, invocation errors and tokens, checking unauthorized tools stay excluded.

### Self-check

1. With hundreds of tools, what goes wrong when all of them go into context? How do tool retrieval and hierarchical routing help?
2. After tool retrieval, the model still picks the wrong tool. How do you separately evaluate relevant-tool recall, argument validity and task outcome?
3. Descriptions of dynamically discovered third-party tools may hide malicious instructions. Design provenance checks and trust boundaries for the tool catalog.

## 10.7 Guardrails, content safety and injection-defense patterns

`core` · Design under constraints and defend tradeoffs

Prerequisites: [10.4 Untrusted data and tool safety](../modules/10.md#unit-10-4)

### Knowledge outline

- Input/output guardrails: moderation APIs, classifiers such as Llama Guard and Qwen3Guard, and rules
- PII detection and redaction (Presidio and similar) across logs and training data
- Jailbreak and injection taxonomies, red-team datasets and automated attack tests
- The lethal trifecta: never combine private data, untrusted content and external communication
- Design patterns: plan-then-execute, dual-LLM isolation, CaMeL-style capability control and action allowlists
- Evaluating false blocks/misses, latency and cost of guardrails and setting release thresholds

### Reading and scope

[Design Patterns for Securing LLM Agents against Prompt Injections](https://arxiv.org/abs/2506.08837) — Proposes six practical prompt-injection defense patterns with ten case studies and discusses the security/utility tradeoff.

All six design patterns and the case studies; read the lethal trifecta for risk combinations and the OWASP Agentic Top 10 for attack surfaces.

### Practical evidence

Add input/output guardrails and one isolation pattern to the P2 workflow agent; measure attack success, false blocks and added latency with injection and jailbreak cases.

### Self-check

1. Explain the lethal trifecta (private data, untrusted content, external communication). Why can’t prompting alone protect an agent that has all three?
2. A deployed content-safety classifier blocks too much and users complain. How do you measure false blocks and misses, and reset the threshold?
3. Compare the ideas and costs of three injection-defense patterns: plan-then-execute, dual-LLM isolation and CaMeL-style capability control.
